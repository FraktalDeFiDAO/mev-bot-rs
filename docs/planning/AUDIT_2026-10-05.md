# Efficiency and profitability audit (2026-10-05)

Static read of the hot path (`mev-engine`, `mev-search`, `mev-risk`, `mev-exec`, `mev-dex`,
`mev-sim`, `config/arbitrum.toml`) plus the measurements already in `DECISIONS.md` and
`SIM_ENGINE.md`. Nothing was built, run or profiled; efficiency items are by inspection. Decisions
that follow from it are #52–#56 in `DECISIONS.md`.

**Bottom line:** the hot path is already fast (pool event to broadcast ≈ 5 ms, E2E fork test). The
bot loses on ordering policy and economics, not on code speed.

## Ordering regime: PGA replaces Timeboost (verify before building on it)

Primary source: the Constitutional AIP "Transition Arbitrum One ordering policy to Priority Gas
Auctions (PGA)" (forum.arbitrum.foundation/t/…/30942). What it says:

- Priority = `min(max_priority_fee_per_gas, max_fee_per_gas - base_fee)`; ties break by earliest
  arrival at the sequencer.
- 125 ms rounds inside 250 ms blocks; a new fast feed publishes ordered txs every round.
- Timeboost is fully removed: no express lane, no 200 ms non-express delay.
- Revenue: 97 % ArbitrumDAO, 3 % Developer Guild.

**Not verified:** the go-live date. The AIP text says activation comes "some time after the vote
passes"; the 2026-09-24 date appears only in press coverage. Our docs written on 2026-10-05 still
assumed FCFS + Timeboost (corrected in `SIM_ENGINE.md`). **First action:** confirm the live ordering
rule against current Arbitrum docs and by observing sequenced blocks (are tip-paying txs placed ahead
of zero-tip ones within a round?). Also confirm the paid fast feed's terms and price.

## Profitability findings

1. **Priority fee hard-coded to 0** (`mev-exec/src/lib.rs`, `sign_and_broadcast`:
   `max_fee_per_gas = base_fee*2`, `max_priority_fee_per_gas = 0`). Under PGA a zero tip is the
   lowest priority in every round. The record so far: 8/8 live arbs lost (#42), then 40 sends / 40
   reverts (#48), mostly "lost by about one block". Fix: tip = fraction of net profit, capped by net
   profit, and included in the on-chain `minProfit` floor so a lost race still reverts instead of
   paying the tip.
2. **No win-rate gating.** Only guards: 500 ms same-route throttle and the $3/day gas cap. Each lost
   race costs ≈ $0.016–0.027. Fix: per-route and per-trigger-source win rate from the existing
   `race` telemetry; send only when `p_win × net − (1 − p_win) × gas > 0`; back off a route after N
   straight losses.
3. **Opportunity set vs. cost per trade.** Opportunities are $0.001–0.014 against $0.016–0.027 gas
   (#23), on the most contested pairs. Liquidations: ≈ $450 of debt in 48 h across all bots on our
   venues (#40), so ≈ $22 of bonus shared across all bots. Fix: weight toward the long tail
   (auto-discovered thin pools, less-watched protocols); measure expected profit per venue before
   adding more lending adapters.
4. **Gas estimate is a fixed formula** (`arb_gas_estimate = 100k + 115k × hops`), calibrated on two
   live receipts. It is the main input to both the profit floor and the on-chain `minProfit`; keep
   re-calibrating from receipts.
   *Retracted:* an earlier version of this audit guessed calldata size was a large share of gas.
   Phase 15 already measured L1 data at 0.2 % of an arb's gas (548 bytes, ~570 gas), so a compact
   encoding would save almost nothing.

## Efficiency findings

1. **Main event loop blocks on network calls** (`mev-engine/src/lib.rs`). In `on_pool_update`,
   `simulate_fast(...).await` runs inline for non-exact routes and in shadow mode; `route()` awaits
   on-demand pool discovery inline; `on_plan` awaits `simulate_liquidation` inline; the 60 s `resync`
   and `rebuild_cycles` (up to 20,000 cycles) also run on the loop. While one runs, pool logs and
   presim events queue behind it. Fix: spawn these as tasks that report back over a channel (as the
   send path already does), with timeouts.
2. **Global `in_flight` flag serializes arbs.** `RiskGuard::check` rejects every non-backrun trade
   until the previous receipt arrives, up to 30 s (`sender.wait(hash, 30 s)`). A dropped tx blocks all
   arbs for that long. Fix: shorten the wait to a few blocks (blocks are 250 ms), then allow N
   concurrent arbs on disjoint pools.
3. **Size search does needless work, but isn't a bottleneck.** `best_size` runs 100 ternary
   iterations × 2 evaluations (≈ 45 reach f64 precision); `amount_out` is a few flops, so this costs
   microseconds. V2 two-pool arbs have a closed form. Low priority.
4. **Minor:** `Sender::send` waits for every endpoint (`join_all`) before returning (bookkeeping
   only, not the broadcast). `max_fee_per_gas = base_fee*2` must cover base fee plus tip once a tip
   exists.

## Already good

Pure, unit- and property-tested search and risk crates; flash swaps (no lender fee, no Balancer
cap); exactness check before sending on the model (#48); marginal-rate prefilter before sizing; cycle
index re-prices only cycles touching the changed pool; background gas-price refresh.

## Suggested order

1. Verify the live ordering rule (above). If PGA is not live yet, items 2–5 still stand; item 1
   (the tip) waits.
2. Priority-fee bid, included in the on-chain floor (#56).
3. Win-rate gating (#57).
4. Move inline awaits off the main loop (#55).
5. Shorten the in-flight wait, then allow concurrent arbs (#56).
6. Long-tail focus: measure expected profit per venue/pair first (#57).
